# REVE 풀필먼트 어드민 재구축 MVP PRD

## 🎯 핵심 정보

**목적**: 동남아 현지 창고 기반 풀필먼트 서비스(보관·재고·포장·배송)의 기존 운영 시스템(REVE)을, 현행 메뉴·상태·용어를 그대로 유지한 채 Next.js 프론트엔드로 재구축한다.
**사용자**: 전체 클라이언트 데이터를 다루는 내부 운영자, 그리고 본인 소유 데이터만 조회·제출하는 클라이언트(화주·셀러 — 화면 표기는 '클라이언트'로 통일).

## 🚶 사용자 여정

```
1. 로그인 페이지
   ↓ 이메일/비밀번호 로그인 성공

2. 입고현황 페이지 (로그인 후 기본 진입 화면)
   ↓ 상단 메뉴 선택

   [공통 메뉴]      → 출고현황 / 반품현황 / 재고현황 / SKU / NEW 페이지로 이동
   [운영자 전용 메뉴] → WMS / 클라이언트 / 사용자 / 업체관리 페이지로 이동
                      (클라이언트 로그인 시 이 메뉴 자체가 노출되지 않음)
   ↓

3. NEW 페이지 (클라이언트가 해외 WMS 담당자에게 요청 제출)
   ↓ 요청 작성(직접 입력 또는 엑셀 업로드) 후 제출

   상태: 제출됨
     ↓ (해외 WMS 담당자에게 이메일 자동 발송 → 담당자 확인 후 WMS 시스템에 수기 등록, 휴먼 인 더 루프)
   상태: WMS 등록 대기
     ↓ (WMS 등록 완료가 자체 DB로 동기화)
   상태: 등록 완료
     ↓ [입고 성격 요청인 경우]

4. 입고현황 페이지에 신규 항목이 입고상태 "예정"으로 반영
   ↓ (물리 입고 진행에 따라 WMS 동기화)
   예정 → 대기 → 입고

5. 로그아웃 클릭 (모든 페이지 공통) → 로그인 페이지로 즉시 리디렉션
```

## ⚡ 기능 명세

### 1. MVP 핵심 기능

| ID | 기능명 | 설명 | MVP 필수 이유 | 관련 페이지 |
|----|--------|------|-------------|------------|
| **[F001]** | 입고현황 조회 | 입고 목록/상세 조회 및 입고상태(예정→대기→입고) 추적 | 물리 입고 진행 확인은 운영 핵심 업무 | 입고현황 페이지 |
| **[F002]** | 출고현황 조회 | 출고 목록/상세 조회 | 출고 처리 현황 확인은 운영 핵심 업무 | 출고현황 페이지 |
| **[F003]** | 반품현황 조회 | 반품 목록/상세 조회 | 반품 처리 현황 확인은 운영 핵심 업무 | 반품현황 페이지 |
| **[F004]** | 재고현황 조회 | 클라이언트별·SKU별 재고 수량 조회 | 입출고 의사결정의 기초 데이터 | 재고현황 페이지 |
| **[F005]** | SKU 관리 | 상품(SKU) 목록 조회 및 등록/수정 | 입출고·재고 데이터의 기준 정보 | SKU 페이지 |
| **[F006]** | NEW 요청 제출 및 상태추적 | 클라이언트가 해외 WMS 담당자에게 상품등록·사은품 등록·라벨 생성 등 요청을 제출(직접 입력 또는 엑셀 업로드), 상태(제출됨→WMS 등록 대기→등록 완료) 추적 | WMS에 직접 쓰기 API가 없어 유일한 등록 진입점 | NEW 페이지 |
| **[F007]** | WMS 연동 관리 | 해외 WMS 등록·연동 관리, 연동 시 해당 WMS의 마켓 목록을 클라이언트 메뉴로 동기화 | WMS 1 : 클라이언트 N 계층의 상위 관리 기능 | WMS 페이지 |
| **[F008]** | 클라이언트 목록 관리 | WMS에서 동기화된 마켓(클라이언트) 목록 조회·관리 | 전체 데이터 스코핑·필터의 기준 정보 관리 | 클라이언트 페이지 |
| **[F009]** | 사용자 계정 관리 | 내부 운영자·클라이언트 사용자 계정 조회 및 발급/수정 | 회원가입이 없어 운영자의 계정 발급이 유일한 신규 사용자 등록 경로 | 사용자 페이지 |

### 2. MVP 필수 지원 기능

| ID | 기능명 | 설명 | MVP 필수 이유 | 관련 페이지 |
|----|--------|------|-------------|------------|
| **[F010]** | 기본 인증 | 로그인/로그아웃만 (회원가입 없음, 운영자가 클라이언트 계정 발급) | 서비스 이용을 위한 최소 인증 | 로그인 페이지 |
| **[F011]** | 업체관리 | 협력 업체 목록 조회 및 등록/수정 | 입출고·배송 운영에 필요한 협력사 정보 관리 | 업체관리 페이지 |
| **[F012]** | 목록 화면 검색 & 엑셀 다운로드 | 기간(시작일/종료일)·기준일자·WMS LINK·상태(ORDER STATUS)·검색어 조합 검색, 검색결과 전체 다운로드 + 행 단위 다운로드, 행 확장(+) 상세 보기, 페이지네이션(Rows per page) | 현행 시스템의 핵심 조회 방식 — 제외 불가 | 입고현황, 출고현황, 반품현황, 재고현황, SKU, NEW 페이지 |
| **[F013]** | 역할별 데이터 스코핑 필터 | 운영자는 클라이언트·국가·WMS LINK 필터 제공(전체 데이터), 클라이언트는 본인 데이터 자동 적용(클라이언트 선택 필터 UI 미노출). 강제는 서버(BFF)에서 처리 | 클라이언트 간 데이터 격리는 서비스의 기본 전제 | 입고현황, 출고현황, 반품현황, 재고현황, SKU, NEW 페이지 |

### 3. MVP 이후 기능 (제외)

- 프로필 상세 관리 (아바타, 자기소개 등)
- 설정 기능 (테마, 언어, 알림 설정)
- 저장된 필터(검색 조건 즐겨찾기) 등 고급 검색
  ※ 기간·기준일자·WMS LINK·상태·검색어 조합의 기본 검색 패널(F012)은 현행 확정 기능 — MVP 필수이며 제외 대상이 아님
- 실시간 알림 시스템
- 정산 메뉴 (현행 시스템에는 존재하나 이번 재구축 범위에서 제외 — 구현 금지)

## 📱 메뉴 구조

```
📱 REVE 내비게이션 (로그인 후 진입 — 비로그인은 로그인 페이지만 접근)

🔑 인증 (비로그인 시)
└── 로그인 - F010

📋 공통 메뉴 (운영자 = 전체 데이터 + 클라이언트·국가·WMS LINK 필터, 클라이언트 = 본인 데이터)
├── 📥 입고현황 - F001, F012, F013
├── 📤 출고현황 - F002, F012, F013
├── ↩️ 반품현황 - F003, F012, F013
├── 📦 재고현황 - F004, F012, F013
├── 🏷️ SKU - F005, F012, F013
└── ✉️ NEW - F006, F012, F013 (WMS 담당자 요청 제출: 상품등록·사은품·라벨 등)

🏢 내부 운영자 전용 메뉴
├── 🗂️ WMS - F007 (해외 WMS 등록·연동)
├── 👥 클라이언트 - F008 (WMS 동기화 마켓 목록)
├── 👤 사용자 - F009
└── 🏭 업체관리 - F011

🔧 공통 (모든 로그인 사용자)
└── 🚪 로그아웃 - F010
```

※ 로그아웃은 별도 화면이 없는 액션이며, 실행 즉시 로그인 페이지로 리디렉션된다 (아래 페이지별 상세 기능의 "로그인 페이지" 항목이 그 대상 화면).

### 🗄️ 백엔드 & 데이터베이스 (기존 운영 시스템 — 이 프로젝트에서 수정 대상 아님)

**이 프로젝트와의 관계**
- 본 프로젝트는 Next.js 프론트엔드이며, 아래 기존 API 서버를 유일한 데이터 소스로 사용한다.
- 백엔드 코드는 이 저장소에 포함되지 않는다. Java 코드 생성/수정 금지.

**시스템 구성**
- API 서버: Java (Spring Boot) 기반 REST API — 클라우드에서 운영 중
- 데이터베이스: 자체 DB (예: MySQL) — API 서버만 접근, 프론트엔드 직접 접근 불가

**데이터 흐름**

**① 조회 — WMS → 프론트엔드 (자동)**
해외 WMS → (배치 수집 / webhook) → 자체 DB 정규화 저장 → REST API → Next.js 프론트엔드
- 동기화 대상: 물류 데이터(입고·재고 등) + 각 WMS에 등록된 마켓(클라이언트) 목록

**② 등록 — 프론트엔드 → WMS (수동, 이메일 기반 휴먼 인 더 루프) — UI 진입점: NEW 메뉴**
클라이언트가 NEW 메뉴에서 요청 작성(직접 입력 or 엑셀 업로드) → 제출 → 자체 DB 저장 (상태: `WMS 등록 대기`)
→ 해외 WMS 담당자에게 이메일 자동 발송 → 담당자 확인 후 WMS 시스템에 수기 등록
→ 이후 ①의 수집 흐름으로 결과가 동기화되면 상태 `등록 완료` 전환

**② 관련 제약/방침**
- 요청 유형: 상품등록, 사은품 등록, 라벨 생성 등 — 유형 목록은 확장 가능하게 설계
- 해외 WMS에 대한 직접 쓰기(Write) API는 없음 — 등록은 반드시 이메일 경유
- 제출 즉시 완료가 아님 → `제출됨 / WMS 등록 대기 / 등록 완료` 중간 상태 관리 필수
- 입고 성격의 요청은 `등록 완료` 후 입고현황에 `예정`으로 동기화되어 물리 입고(예정→대기→입고)를 추적
- 엑셀 업로드: 템플릿 다운로드 제공, 업로드 시 형식 검증 후 제출
- 이메일 발송 주체: TBD — 기존 Java API에 해당 엔드포인트가 있는지 확인 필요.
  없다면 Next.js 서버(Route Handler)에서 발송 처리

- 인증: TBD (예: Bearer JWT)
- 응답 형식: JSON (예: `{ code, data, message }` 래핑 여부 확인 필요)

### 🚀 배포 & 호스팅 (확정)

**인프라**
- AWS EC2 1대에서 운영 — 기존 Java API 컨테이너와 신규 Next.js 컨테이너 동거
- Next.js: Docker 컨테이너, docker compose로 관리
- 이미지 레지스트리: ECR

**컨테이너 네트워크**
- 두 컨테이너를 공유 Docker 네트워크로 연결
  - 최초 1회: `docker network create app-net`
  - 기존 Java API 컨테이너를 `app-net`에 연결
    (compose 관리 시 networks 항목 추가, docker run 관리 시 `docker network connect app-net <java-container>`)
  - Next.js compose에서 `app-net`을 external network로 참조
- Next.js(서버) → Java API: `http://<java-container-name>:8080` (컨테이너명 DNS)
- 기본 bridge 네트워크는 컨테이너명 DNS 미지원 → 반드시 사용자 정의 네트워크 사용
- 브라우저 → Java API 직접 호출 금지, Next.js Route Handler(BFF) 경유. CORS 불필요
- Java 컨테이너 자체는 변경 없음 (네트워크 연결만 추가)

**트래픽 라우팅**
- Nginx 리버스 프록시: `/` → Next.js(3000) (TBD: 기존 Nginx 유무 확인)
- HTTPS: Nginx + Let's Encrypt 또는 ALB (TBD)

**빌드 요구사항**
- `next.config.js`: `output: 'standalone'` 필수
- Dockerfile: multi-stage build, node:20-alpine
- ⚠️ 이미지 빌드는 CI(GitHub Actions)에서 수행 → ECR push, EC2는 pull & up만
  (소형 인스턴스에서 next build 시 OOM으로 Java API까지 영향 위험)

**환경 변수**
- `API_BASE_URL=http://<java-container-name>:8080` (서버 전용, NEXT_PUBLIC 아님)
- `.env`는 EC2에만 존재, git/이미지 포함 금지

**배포 절차**
GitHub Actions → 빌드 → ECR push → EC2에서 pull → `docker compose up -d`

**개발 방침**
- Dockerfile, compose.yml, .dockerignore는 초기 작성 후 로컬 검증
- EC2 실배포는 UI 완성 이후 진행
